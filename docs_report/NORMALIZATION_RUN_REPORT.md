# Отчёт о прогоне нормализации

Дата прогона: 27 июня 2026. Ветка: feat/normalization-unblock.
Стек: docker compose (Postgres 16 + pgvector, Redis, FastAPI, Celery).
Ключи AI на прогоне: отсутствуют (путь code + exact + fuzzy, без эмбеддингов и реранкера).

## Что подтверждено

| Задача | Результат |
|---|---|
| A. Маппинг загрузчика | `seed-reference "Справочник услуг.xlsx"` загрузил **1231 услугу** (1281 строк, дедуп по паре имя + код тарификатора). У записей заполнены category (специальность) и icd_code (код тарификатора). Блокер снят. |
| B. Level 0 матч по коду | Работает. Одиночный код тарификатора даёт уверенность 0.98, неоднозначный 0.95. **1489 позиций** сопоставлены методом `code` (наибольшая доля матчей). Клиника 3: **74 позиции** по коду. |
| C. Снят фильтр по категории | Семантика и лексика больше не отсекают кандидата по неравенству категории (специальность справочника против раздела прайса). |
| E1. .xls (Клиника 7) | LibreOffice headless в образе сконвертировал .xls: **2864 позиции**, читаемые русские названия (Иммуноглобулин М, Комплемент С3). Локально без LibreOffice путь даёт 0, в Docker работает. |
| E2. Сканы (Клиника 2 2026, Клиника 3) | Встроенный текстовый слой читаем (детектор не пометил как битый), извлечены русские названия без артефактов. ПереOCR на этих файлах не потребовался. |
| Версионирование (демо) | Услуги, сопоставленные в обоих прайсах Клиники 1 (2024 DOCX и 2026 PDF), строят историю цен: Гепатит B HBsAg 3830 → 5430, Прием эпилептолога 10000 → 13900, IgG общий 2950 → 4180. |

## Метрики прогона (GET /stats)

- Документов: 10, все обработаны.
- Позиций всего: 18 435. Активных (после версионирования): 16 748.
- Сопоставлено методами code/exact/fuzzy (всего по базе): **2983** позиции
  (code 1489, fuzzy 1160, exact 334).
- Автонормализация активных позиций (метрика /stats): **7.7%**.
- Доля когда либо автосопоставленных позиций: **16.2%**.
- Очередь needs_review: 15 555. unmatched: 5.

Разница между 7.7% и 16.2% объясняется версионированием: сопоставленные
позиции схлопываются между годами (старая версия архивируется), несопоставленные
остаются активными. То есть активная метрика занижает реальное качество матча.

## Главный вывод: порог 70% упирается в эмбеддинги, а не в код

Цель ТЗ 70% автоматча на этом прогоне не достигнута, и причина структурная, а не в правках A/B/C.

Распределение позиций по верхнему лексическому баллу (RapidFuzz) против справочника:

| Полоса | Доля | Что это |
|---|---|---|
| code + exact | 11.4% | детерминированный матч, авто |
| fuzzy ≥ 0.85 | 5.9% | лексический авто |
| 0.60 – 0.85 | 26.9% | пограничная зона (адресуется LLM арбитром) |
| **0.40 – 0.60** | **52.7%** | **смысловое совпадение без лексического (нужны эмбеддинги)** |
| < 0.40 | 3.1% | мусор извлечения или нет в справочнике |

Больше половины позиций (52.7%) лежат в полосе 0.40 – 0.60: смысл совпадает,
а слова разные («Консультативный прием врача акушера» против справочного
«Прием акушер-гинеколога»). Эти случаи закрывают только эмбеддинги
(семантический кандидатогенератор, уровень 3 каскада). Даже идеальный LLM арбитр
по всей пограничной полосе даёт потолок ~44%.

Архитектура (раздел 5.1) ставит эмбеддинги OpenAI text-embedding-3-large
основным кандидатогенератором. На прогоне доступен только ключ Anthropic
(LLM арбитр), ключа эмбеддингов (OpenAI или Voyage) нет, поэтому уровень 3
выключен, и матч держится на коде и лексике.

## Что даст 70%

1. **Ключ эмбеддингов** (OpenAI text-embedding-3-large, dim 3072, или Voyage).
   Это основной рычаг: закрывает полосу 0.40 – 0.60. Прогнать
   `seed-reference` заново (досчитает Service.embedding), затем `ingest docs`.
2. Закалка извлечения (issue склейки многострочных названий): чище
   service_name_raw поднимает и лексику, и эмбеддинги, и убирает мусор из знаменателя.
3. Тюнинг порога `MATCH_HIGH_THRESHOLD` 0.85 → 0.80 (раздел Task D): малый эффект
   (несколько процентов), без эмбеддингов 70% не даёт.

## Воспроизведение

```bash
cp .env.example .env            # для 70% впишите OPENAI_API_KEY (эмбеддинги)
docker compose up --build -d
docker compose exec backend python -m app.cli seed-reference "Справочник услуг.xlsx"
docker compose exec backend python -m app.cli ingest docs
# метрики: GET http://localhost:8000/stats
```

# Прогон 2: активация эмбеддингов (feat/embeddings-activation)

Дата: 27 июня 2026. Ключ OpenAI добавлен в gitignored .env. Реранк и LLM арбитр
в этой фазе НЕ запускались (по ТЗ). Порты вынесены в .env (APP_PORT 8088 и т.д.).

## Что подтверждено

- `Service.embedding` заполнен у **1231 из 1231** услуги (text-embedding-3-large, dim 3072).
- Эмбеддинги кэшируются: **13 426** уникальных текстов в ai_cache (справочник + названия позиций).
- Семантический уровень каскада работает: метод `embedding` появился в матчах.

## Метрики (честно)

| Порог автоматча | Авто (активные) | Авто (всего, ever-matched) | Точность эмбеддинг-матчей |
|---|---|---|---|
| 0.85 (дефолт) | 8.0% | около 16% | высокая, но почти нет матчей (косинус редко > 0.85) |
| **0.70** (обоснован) | **16.3%** | **37.5%** | около 94% (выборка 18 позиций, 17 верны) |
| 0.55 | около 40% активных / 78% по симуляции | — | около 50% (половина матчей НЕВЕРНЫ) |

Без эмбеддингов (Прогон 1) ever-matched было 16.2%. С эмбеддингами на пороге 0.70
ever-matched **37.5%** — рост более чем вдвое.

Разница активной метрики (16.3%) и ever-matched (37.5%): версионирование
архивирует сопоставленные дубликаты между годами (К1 2024 и 2026 схлопываются),
несопоставленные остаются активными. Активная метрика /stats занижает качество.

## Достигнут ли порог 70%? Нет, и вот честная причина

Численно 70% достигается понижением порога до ~0.55, НО точность там падает до ~50%:
половина эмбеддинг-матчей неверна. Примеры неверных при score 0.55 0.68:

- «Измерение скорости оседания эритроцитов» (СОЭ) -> «Кардиологический Check-Up»
- «Взятие мазка на пцр» -> «Корь ПЦР»
- «Консультация невропатолога» -> «Прием эпилептолога»

Это была бы подгонка цифры, а не качество. На честном пороге 0.70 (точность ~94%)
автоматч 16.3% активных / 37.5% всех.

Примеры ВЕРНЫХ эмбеддинг-матчей при score 0.70+ (точность ~94%):

- «Рентгенография одной кисти» -> «Рентген кисти»
- «Первичный прием врача эндокринолога» -> «Прием эндокринолога»
- «Определение прямого билирубина» -> «Билирубин прямой»
- «Повторный прием врача офтальмолога» -> «Прием окулиста»

## Что реально дали эмбеддинги: RECALL

Эмбеддинги это кандидатогенератор. Их вклад не столько в авто-проценте, сколько в
том, что правильная услуга теперь стоит в топе кандидатов даже когда слова разные.
Выборка показывает: при score 0.70+ верный кандидат на первом месте в ~94% случаев,
и часто верен уже при 0.60 0.70. Это денежный экран очереди верификации: оператор
выбирает верную услугу в один клик, а не ищет вручную.

## Путь к 70% с сохранением точности (следующая фаза)

1. **Реранк (Cohere) + LLM арбитр.** Эмбеддинги дают высокий recall (верный
   кандидат в топ-20). Реранк переупорядочивает топ так, что верный поднимается
   на первое место с высоким баллом, а LLM арбитр подтверждает пограничные.
   Именно эта связка превращает recall в точный автоматч семантической зоны.
   В этой фазе они исключены по ТЗ.
2. **Закалка извлечения (issue #1).** В знаменателе 18 435 позиций много мусора
   извлечения (обрывки многострочных названий). Чистый знаменатель поднимает
   процент без потери точности.

## Бюджет OpenAI

13 426 уникальных текстов, ориентировочно 160 тысяч токенов,
text-embedding-3-large по 0.13 USD за 1M -> около **0.02 USD**. Кэшируется,
повторные прогоны почти бесплатны. Существенно меньше 1 USD. Точная цифра в
дашборде OpenAI.

## Порты

Хост-порты вынесены в .env с выделенными дефолтами (APP_PORT 8088, DB_PORT 5544,
REDIS_PORT 6399, FRONTEND_PORT 5577). Никакого динамического ремапа по чужим
проектам. Нужен 8000 — одна строка `APP_PORT=8000` в .env.

# Прогон 3: слой LLM-арбитра на выборке (feat/normalization-arbiter)

Дата: 28 июня 2026. Ветка: feat/normalization-arbiter (issue #4, #19).
Доступен только ключ OpenAI (заново выпущенный, gitignored .env). Ключа Cohere
нет → **реранк не запускался** (gracefully пропущен). Арбитр — на ДЕШЁВОЙ модели
**gpt-4o-mini** (не opus), провайдер выбран по доступному ключу.
Прогон ТОЛЬКО на выборке пограничных позиций; ПОЛНЫЙ прогон НЕ запускался.

## Issue #19: graceful-degradation внешних AI-вызовов

Все три клиента (эмбеддинги, реранк, арбитр) теперь при сетевой/HTTP/битом ответе
ловят ошибку, логируют и возвращают None — каскад деградирует на лексику ровно как
при отсутствии ключа, документ не падает. Покрыто юнит-тестами (tests/test_ai_graceful.py:
ConnectError, HTTP 5xx, битый payload, путь без ключа, happy-path; 18 тестов).

## Метод замера (честный знаменатель)

Истину берём из кода тарификатора: позиция, чей код резолвится в РОВНО ОДНУ услугу
справочника, имеет известную правильную пару. Это честный знаменатель — «позиции с
реальной парой в справочнике». На них гоняем ТЕКСТОВЫЙ каскад (код намеренно
игнорируем, code=None), берём пограничную зону [0.60, 0.85) — именно её адресует
арбитр — и сравниваем его выбор с код-истиной. price_items только читаем; пишем лишь
в ai_cache (кэш вердиктов).

| Параметр выборки | Значение |
|---|---|
| Активных позиций с кодом тарификатора | 8044 |
| **Честный знаменатель** (код → ровно 1 услуга справочника) | **583** |
| Пограничных [0.60, 0.85) среди них (выборка прогона) | **341** |
| Из них правильная услуга есть в кандидатах (recall-потолок) | 292 / 341 = **85.6%** |

## Результаты выборки (арбитр gpt-4o-mini)

| Метрика | Значение |
|---|---|
| Baseline авто на этой полосе (без арбитра) | 0 (по построению score < 0.85) |
| Арбитр выбрал услугу | 264 / 341 = 77.4% |
| ↳ точность выбора (== код-истина) | 231 / 264 = **87.5%** |
| **Прирост авто** (score ≥ 0.85 после арбитра) | 251 / 341 = **73.6%** |
| ↳ точность авто-матчей | 223 / 251 = **88.8%** |

Арбитр превращает пограничную зону (которая иначе уходит в needs_review) в
авто-матч: +73.6 п.п. авто на этой полосе при точности ~89%. Потолок задаёт recall
кандидатов (85.6%): где правильной услуги нет в топе, арбитр выбрать её не может —
это закрывается реранком (нужен ключ Cohere).

## Проекция на полный прогон (оценка, НЕ запускался)

Пограничная полоса [0.60, 0.85) — по Прогону 1 это **26.9%** позиций, то есть
≈ 4500–5000 активных позиций на всей базе. При удельной цене ~$0.000049 за вызов
полный прогон арбитра ≈ **$0.22–0.30** (эмбеддинги уже в кэше, повторно почти
бесплатны). Цифра в пределах разумного, но точное число пограничных требует
отдельного измерительного прохода.

## СТОП и рекомендация владельцу

Выборка выполнена, слой арбитра работает и измерен. **Полный прогон не запускался —
решение за владельцем** (ограниченный бюджет). Рекомендация:

1. Полный прогон арбитра на пограничной полосе оправдан: ~$0.25 за +авто в
   семантической зоне при точности ~89%. Запуск: `app.cli` ingest/rematch с
   выставленным `OPENAI_API_KEY` и `LLM_ARBITER_MODEL=gpt-4o-mini`.
2. Реранк (Cohere) поднимет recall-потолок выше 85.6% — правильный кандидат чаще
   попадёт в топ, и арбитр сможет его подтвердить. Нужен ключ Cohere; без него
   слой gracefully выключен.
3. Полоса 0.40–0.60 (52.7%, Прогон 1) арбитром не закрывается — это работа
   эмбеддингов (уже включены) и чистки извлечения, а не арбитра.

## Воспроизведение

Поднять Postgres с данными Прогона 2 (том `medarchive_postgres_data`), затем на
выборке: разметить позиции по коду (код → ровно 1 услуга), прогнать текстовый
каскад без кода, отобрать [0.60, 0.85), включить арбитр (`LLM_ARBITER_MODEL=
gpt-4o-mini`, ключ OpenAI из gitignored .env) и сверить выбор с код-истиной.
Ключи в репозиторий не коммитятся.
